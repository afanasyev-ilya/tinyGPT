GDN: что такое o и где настоящий цикл

Путь одного токена: hidden state → Q/K/V → recurrent state → output слоя → logits → следующий token ID. И почему в TensorRT‑LLM trace нет тысячи маленьких matmul.

1. Базовый цикл

После токенизации мы имеем IDs формы [B,T]. Embedding превращает каждый ID в hidden-вектор xᵢ длины C. Внутри каждого слоя x уже означает не token ID, а активации этого слоя формы [B,T,C].

for i in range(T):
    q_i = W_q @ x_i       # [d_k]
    k_i = W_k @ x_i       # [d_k]
    v_i = W_v @ x_i       # [d_v]

    S_i = S_prev + outer(v_i, k_i)  # [d_v, d_k]
    o_i = S_i @ q_i                 # [d_v]

    S_prev = S_i
ОбъектФорма одной головыСмысл
xᵢ[C]Вход текущего слоя
qᵢ, kᵢ[d_k]Адрес чтения и адрес записи
vᵢ[d_v]Содержимое записи
Sᵢ[d_v,d_k]Матрица ассоциативной памяти
oᵢ[d_v]Результат чтения из памяти в этом слое
oᵢ — не следующий токен. Это промежуточный output одного GDN/attention sublayer для позиции i.

2. Как из oᵢ получается следующий токен

Outputs голов объединяются, проходят output projection и возвращаются в residual stream:

yᵢ = Wo oᵢ,    x′ᵢ = xᵢ + yᵢ

После этого идут MLP/MoE и остальные слои. Только hidden state последнего слоя переводится LM head’ом в logits по словарю.

3. Prefill → decode → decode

Семантически prefill четырёх токенов обязан быть causal: первому output доступен только первый токен, второму — первые два и так далее.

# prefill
S_0 = zeros(...)
o_1, S_1 = step(S_0, q_1, k_1, v_1)
o_2, S_2 = step(S_1, q_2, k_2, v_2)
o_3, S_3 = step(S_2, q_3, k_3, v_3)
o_4, S_4 = step(S_3, q_4, k_4, v_4)

# После prefill S_1..S_3 больше не кэшируются; остаётся S_4.

# первый decode
o_5, S_5 = step(S_4, q_5, k_5, v_5)

# второй decode
o_6, S_6 = step(S_5, q_6, k_6, v_6)

Нельзя сначала построить S₄, а потом посчитать o₁=S₄q₁: в o₁ протекла бы информация из будущих позиций 2–4. Однако хранить после prefill нужно только конечный S₄.

Тонкая поправка: читать S на каждом шаге нормально. Это матрица фиксированного размера, поэтому цена S @ q не растёт с длиной контекста. Мы избегаем не чтения state, а повторного прохода по всем старым K,V и повторного построения state с нуля.

4. Delta rule применяется и в prefill, и в decode

Additive update S += outer(v,k) уже даёт linear-time recurrence и фиксированный cache. Но старые записи никогда не удаляются, нормы state могут расти, а похожие keys складывают конфликтующие values в одни направления. Delta rule решает это не усреднением, а чтением старой записи и записью только ошибки.

Короткая версия: главное правило α и β

α отвечает за старую память целиком. Сначала весь state умножается на α: при α≈1 почти всё помним, при маленьком α быстро забываем.

β отвечает за текущую запись. После decay модель смотрит, что state уже возвращает для текущего key, и сдвигает это значение к новому v: при β=0 не пишет ничего, при β=1 заменяет запись полностью.

# 1. Состарить всю память
S = alpha * S

# 2. Узнать, что сейчас записано по текущему key
old = S @ k

# 3. Приблизить old к новому value; beta задаёт размер шага
correction = beta * (v - old)
S = S + outer(correction, k)

# 4. Прочитать output текущей позиции
o = S @ q

Если key нормирован и мы после update читаем по тому же key, всё сводится к одной строке:

новая запись = (1−β) · α · старая запись + β · новое value.

Мини-пример: state хранит две независимые записи [10,20]; текущий key указывает на первую, и мы хотим записать туда 4.

αβРезультатПо-человечески
10[10,20]Всё оставить как есть
10.5[7,20]Пройти половину пути от 10 к 4
11[4,20]Заменить 10 на 4
0.50[5,10]Забыть половину всей памяти, ничего не писать
0.51[4,10]Забыть половину всего, затем точно записать 4

Коротко: α — «сколько оставить от прошлого», β — «насколько поверить новой записи». Оба коэффициента GigaChat вычисляет заново для каждого токена, GDN-слоя и value-head; это не две константы на всю модель.

def gated_delta_step(S, q, k, v, alpha, beta):
    S = alpha * S                  # глобально забываем
    old_value = S @ k              # что уже записано по адресу k
    error = beta * (v - old_value) # насколько исправить запись
    S = S + outer(error, k)        # rank-one update
    o = S @ q                      # читаем для текущей позиции
    return o, S

Именно эта функция step семантически используется для всех четырёх prompt-токенов, затем для token 5, затем для token 6. Delta rule — часть определения GDN, а не специальный режим decode.

Что именно делает β

Сначала временно положим α=1. Для нормированного key, то есть kᵀk=1, прочитаем обновлённый state по тому же key:

S′k = Sk + β(v − Sk)(kᵀk) = (1−β)Sk + βv.

Это точная интерполяция между старым предсказанием Sk и новым target v:

  • β=0 — проигнорировать текущую запись;
  • β=0.25 — пройти четверть пути от старого value к новому;
  • β=1 — полностью заменить value для направления k.

Для любого направления u, ортогонального текущему key (kᵀu=0), delta update ничего не меняет:

S′u = Su + β(v−Sk)kᵀu = Su.

Поэтому β — это одновременно learning rate fast-weight памяти и сила точечной перезаписи.

Что именно делает α

Перед delta update GDN умножает весь state на α∈(0,1):

S̄ = αS,    S′ = S̄ + β(v−S̄k)kᵀ.

Для нормированного текущего key:

S′k = (1−β)α(Sk) + βv.

А для ортогонального направления u:

S′u = αSu.

То есть delta/β может восстановить или заменить текущую ассоциацию, а все нетронутые направления просто стареют с коэффициентом α.

Численный пример

Пусть state одной value-размерности равен S=[10,20], текущий k=[1,0], а новое v=4. Второй элемент state соответствует ортогональному направлению и текущей записью не затрагивается.

αβНовый stateЧто произошло
10[10,20]Новую запись проигнорировали
10.25[8.5,20]25% пути от 10 к 4
11[4,20]Точно заменили первую ассоциацию
0.50[5,10]Только глобальное затухание
0.50.25[4.75,10]Decay, затем частичная запись 4
0.51[4,10]Первую запись восстановили до 4, вторая затухла

Как модель выбирает α и β

В TRT‑LLM/GigaChat это data-dependent величины для каждого токена и головы. Из дополнительных projections aᵢ,bᵢ вычисляется:

gᵢ = −exp(Alog) softplus(aᵢ + dtbias),    αᵢ=exp(gᵢ),    βᵢ=sigmoid(bᵢ).
  • Большой положительный aᵢ+dt_bias делает α меньше: сильнее очистить старую память.
  • Сильно отрицательный aᵢ+dt_bias даёт α около 1: сохранить память.
  • Большой bᵢ даёт β около 1: активно записать/заменить.
  • Сильно отрицательный bᵢ даёт β около 0: почти не учиться на этом токене.

A_log и dt_bias задают базовый timescale головы, а projections aᵢ,bᵢ позволяют менять forget/write behavior в зависимости от содержимого токена.

Как затухает старая запись во времени

Если некоторое направление долго не получает корректирующих delta-записей, его вклад между позициями j и t умножается на произведение gates:

memory from j at t ∝ αj+1 αj+2 … αt.

При постоянном α старая информация убывает экспоненциально. Например, примерный half-life равен log(0.5)/log(α): для α=0.9 это около 6.6 токена, для 0.99 — 69, для 0.999 — 693. В настоящем GDN α меняется на каждом токене, поэтому модель сама выбирает, когда удерживать state, а когда быстро его стереть.

5. Есть ли такой цикл в реальном TensorRT‑LLM?

Как математическая зависимость — да. Как последовательность маленьких PyTorch matmul/kernel launches в prefill — нет.

Почему recurrence можно перегруппировать

Один GDN step можно записать как аффинное преобразование state:

Sᵢ = Sᵢ₋₁ Pᵢ + Hᵢ

где

Pᵢ = αᵢ(I − βᵢkᵢkᵢᵀ),    Hᵢ = βᵢvᵢkᵢᵀ.

Подставляем первый шаг во второй и раскрываем скобки:

S₁ = S₀P₁ + H₁.
S₂ = S₁P₂ + H₂ = (S₀P₁+H₁)P₂+H₂ = S₀P₁P₂+H₁P₂+H₂.

Продолжаем подстановку:

S₃ = S₀P₁P₂P₃ + H₁P₂P₃ + H₂P₃ + H₃.
S₄ = S₀P₁P₂P₃P₄ + H₁P₂P₃P₄ + H₂P₃P₄ + H₃P₄ + H₄.

И для chunk из 64 токенов:

S₆₄ = S₀(P₁…P₆₄) + Σᵢ₌₁⁶⁴ Hᵢ(Pᵢ₊₁…P₆₄).

Весь chunk можно концептуально свернуть в одну пару:

Pchunk=P₁…P₆₄,    S₆₄=S₀Pchunk+Hchunk.
Именно так нужно понимать «TRT‑LLM разворачивает до S₆₄». Результат математически эквивалентен этому раскрытию, но runtime не создаёт 64 полные матрицы Pᵢ и не строит огромную формулу буквально.

Каждый Pᵢ имеет специальный вид αᵢ(I−βᵢkᵢkᵢᵀ): изменение относительно identity является rank-one. TRT‑LLM/FLA использует эту структуру и более экономичное WY-представление, чтобы не материализовать полные Pᵢ, а превратить работу в GPU-friendly matrix multiplies и triangular solve.

Кроме конечного S₆₄, prefill обязан получить causal outputs oᵢ=Sᵢqᵢ для всех позиций. Поэтому chunk algorithm вычисляет также эквиваленты prefix-переходов 1, 1…2, …, 1…64. В persistent cache после chunk остаётся только его конечный state.

Что происходит в prefill trace

В текущем TRT‑LLM путь chunk_gated_delta_rule разбивает работу примерно на такие стадии:

  1. cumulative log-gate внутри chunk;
  2. chunk-local взаимодействия K Kᵀ;
  3. triangular solve;
  4. построение WY/update-представления;
  5. обновление state и вычисление outputs крупными tiled kernels.

Поэтому в Nsight/CUDA trace видны несколько сравнительно крупных kernels на chunk/stage, а не T запусков вида «матрица × вектор». При четырёх токенах весь prompt помещается в один chunk. При длинном prompt chunks обрабатываются с передачей граничного state между ними.

Что происходит в decode trace

При обычном decode T=1. Fused recurrent kernel за один launch:

загружает S из request state pool
вычисляет alpha и beta
нормализует q/k
делает decay + delta update + read
записывает новый S обратно

Даже если внутри kernel есть цикл по небольшому T (например, verify нескольких draft tokens), это device-side loop внутри одного kernel, а не цепочка видимых снаружи маленьких matmul.

6. Как это сочетается в GigaChat

Каждый слой владеет собственным cache. GDN не сжимает KV cache соседнего attention-слоя:

GDN layer 0       хранит S^(0) + короткий conv state
GDN layer 1       хранит S^(1) + короткий conv state
Attention layer 2 хранит свой растущий KV cache
GDN layer 3       хранит S^(3) + короткий conv state

Текущий token hidden state последовательно проходит эти слои. Attention-слой дописывает свои K/V; GDN-слой поглощает свои текущие k/v в собственный фиксированный state.
